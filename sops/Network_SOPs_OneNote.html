Switch firmware upgrade (any model, Cisco or Aruba)

PartDetail
PurposeUpgrade the operating system on any Cisco (IOS-XE / IOS) or Aruba (AOS-CX) switch or stack
When to useScheduled firmware upgrade, security advisory, or bug fix needing a newer release
OutageYes: the switch reboots, so connected users, phones and APs drop. Book a maintenance window

Process (same for every switch)

  1. Choose the release: latest supported for the model, for best practice and security. Cisco: prefer the suggested (gold star) release. Aruba: prefer the recommended release on the support portal. Read the release notes for the upgrade path.

  2. Approve: change approval and a maintenance window.

  3. Record the current state: version, stack members, port status, neighbours, spanning tree, PoE.

  4. Back up the config off the box (see the backup SOP).

  5. Check the image: compare its hash with the published one (e.g. sha256sum <file> on the server) before loading it.

  6. Load the image to the switch.

  7. Boot the new image and wait. Don't power off during the first boot.

  8. Check it worked against the records from step 3.

  9. Roll back to the old image if checks fail.

Load imagecopy <url>/cat9k_iosxe.<version>.SPA.bin flash:copy tftp://<server-ip>/<image>.swi secondary (load into the slot not currently booted)
Verify on switchverify /md5 flash:<image>show images (check the version in that slot)

Notes

  • Aruba keeps two image slots. Always load the new image into the slot you're not booted from, so the old one stays as the rollback.

  • Aruba VSX pairs: vsx update-software upgrades one switch at a time, so the pair stays up.

  • Older platforms have different syntax: Cisco classic IOS (e.g. 2960-X) and ArubaOS-Switch (e.g. 2930F). Check the model's guide.

  • If the image comes from the internal repository, check the switch can reach the cache first (see the ISR SOP).

  • Model-specific detail: see the Catalyst SOP further down this section.

Router firmware upgrade (any model, Cisco or Aruba)

PartDetail
PurposeUpgrade the operating system on any Cisco router (IOS-XE / IOS) or Aruba gateway (ArubaOS / AOS 10)
When to useScheduled firmware upgrade, security advisory, or bug fix needing a newer release
OutageYes: the router reboots, so the site loses WAN and internet access. Book a maintenance window

Aruba doesn't make traditional routers. Its routing devices are gateways (branch and mobility gateways, managed by CLI or Aruba Central) and EdgeConnect SD-WAN appliances (managed by Orchestrator).

Process (same for every router)

  1. Choose the release: latest supported for the model, for best practice and security. Cisco: prefer the suggested (gold star) release. Aruba: prefer the recommended release. Read the release notes for the upgrade path.

  2. Approve: change approval and a maintenance window. Tell the site: WAN and internet go down during the reboot.

  3. Record the current state: version, interfaces, routing table size, routing neighbours, VPN tunnels.

  4. Back up the config off the box.

  5. Plan remote access: if the upgrade fails you may lose remote access to the site. Have someone on site, or console access, ready.

  6. Check the image: compare its hash with the published one before loading it.

  7. Load the image to the router.

  8. Boot the new image and wait.

  9. Check it worked against the records from step 3.

  10. Roll back to the old image if checks fail.

OneNote section: Device upgrades  ·  Page: IOS-XE upgrade on an ISR via the caching server

IOS-XE upgrade on an ISR via the caching server

PartDetail
PurposeUpgrade IOS-XE on an ISR 4300, downloading the image from the internal repository through the regional caching server (CACHE-SRV)
When to useScheduled firmware upgrade, security advisory, or bug fix needing a newer release
OutageYes: the router reloads. Book a maintenance window

Before you start

  1. Choose the release: the latest supported release for the model, for best practice and security. On Cisco's download page, prefer the suggested (gold star) release. Check the release notes for the upgrade path and open security advisories. Then get change approval and a maintenance window.

  2. Record the current state: show version (release, install or bundle mode), show ip interface brief, show ip route summary, routing neighbours.

  3. Check free space: dir bootflash:. Free space must be larger than the image. Remove old unused images if needed.

  4. Back up the config: copy running-config startup-config, then copy it to the backup server.

  5. Check the download source interface: show run | include source-interface. Look for ip http client source-interface.

  6. Test reach to the cache with that source: ping <CACHE-SRV-IP> source <source-interface>. If it fails, fix this first (see Troubleshooting below).

  7. Get the image's published MD5 hash.

Steps

  1. Download the image:

    • copy http://repo.example.internal/firmware/isr4300-universalk9.<version>.SPA.bin bootflash:

    • The request goes to the repository URL, but CACHE-SRV answers it if it holds a local copy. This is invisible at the CLI.

  2. Verify the file: verify /md5 bootflash:isr4300-universalk9.<version>.SPA.bin. It must match the published hash.

  3. Install. Check the mode from show version:

    • Install mode: install add file bootflash:isr4300-universalk9.<version>.SPA.bin activate commit. Answer yes to the reload prompt.

    • Bundle mode: no boot system, then boot system flash bootflash:isr4300-universalk9.<version>.SPA.bin, then write memory, then reload.

Check it worked

  • show version shows the new release.

  • Install mode: show install summary shows the new package as committed.

  • Interfaces, routes and neighbours match the pre-check records.

  • Services on the site work (users, phones, internet).

Roll back

  • Install mode: show install rollback to list rollback points, then install rollback to id <id>.

  • Bundle mode: point boot system back to the old image, write memory, reload.

  • Keep the old image on bootflash until the new one is proven stable.

Troubleshooting the download

SymptomLikely causeFix
Copy times out or failsSource IP's subnet has no route or permit to CACHE-SRV (e.g. Loopback0 in VLAN X)ping <CACHE-SRV-IP> source <int> to confirm. Set ip http client source-interface to an interface that has access, or get the subnet added
Download is much faster than expectedServed from CACHE-SRVNormal. Still check the MD5
MD5 mismatch or wrong versionStale or corrupt copy on the cacheDelete the file, retry once, then raise it with the team that runs the cache

Notes

  • Check the source interface before blaming a bad file or a dead cache. From the CLI they all look the same.

  • Background: CCNA vs Real World entries "Regional Caching Redirect" and "Cache Server Unreachable When Sourced from Loopback0".

OneNote section: Device upgrades  ·  Page: Cisco IMC (CIMC) firmware update on a UCS server

Cisco IMC (CIMC) firmware update on a UCS server

PartDetail
PurposeUpdate CIMC, BIOS, adapter and storage firmware on a UCS C-Series server or E-Series module, using the Host Upgrade Utility (HUU)
When to useScheduled firmware upgrade, security advisory, or a new OS version that needs newer firmware
OutageYes: the server reboots, so everything running on it goes down. CIMC-only updates restart CIMC but not the host

Before you start

  1. Choose the release: the latest supported HUU for the exact server model, for best practice and security. Prefer Cisco's suggested (gold star) release.

  2. Read the release notes for the upgrade path. Some older versions need an in-between version first.

  3. Record current versions: Admin → Firmware Management in the CIMC web page, or show version over SSH.

  4. Get change approval and a maintenance window. Tell the owners of services running on the server.

  5. Shut down the OS or VMs on the server cleanly.

Steps (HUU, recommended)

  1. Download the HUU ISO for the model from Cisco. Check its MD5 against the published hash.

  2. Log in to the CIMC web page and open Launch KVM.

  3. In the KVM, attach the ISO under Virtual Media.

  4. Power-cycle the server. Press F6 for the boot menu and choose the virtual DVD.

  5. In the HUU, choose Update All. Wait for it to finish, then let it reboot.

Newer CIMC releases can run the HUU from the web page with no KVM. Look under Admin → Firmware Management.

Steps (CIMC only, via SSH)

Use only if the release notes say the new CIMC works with the current BIOS.

  1. scope cimc

  2. scope firmware

  3. update tftp <tftp-server-ip> <path>/<cimc-image>.bin

  4. activate (CIMC restarts; the host keeps running)

Check it worked

  • Admin → Firmware Management shows the new CIMC, BIOS and adapter versions.

  • Chassis → Faults and Logs shows no new faults.

  • The OS boots and its services work.

Roll back

  • CIMC keeps a backup image. Under Admin → Firmware Management, activate the backup image to go back.

  • For BIOS and adapters, run the HUU for the previous release.

Notes

  • Keep CIMC and BIOS on versions released together. The HUU does this for you.

  • E-Series in an ISR: reach CIMC from the router with ucse subslot <slot> session imc.

OneNote section: Device upgrades  ·  Page: Cisco Catalyst switch IOS-XE upgrade (single switch or stack)

Cisco Catalyst switch IOS-XE upgrade (single switch or stack)

PartDetail
PurposeUpgrade IOS-XE on a Catalyst 9000 switch or stack, using install mode
When to useScheduled firmware upgrade, security advisory, or bug fix needing a newer release
OutageYes: every switch in the stack reloads, so all connected users, phones and APs drop. Book a maintenance window

Before you start

  1. Choose the release: the latest supported release for the model, for best practice and security. Prefer Cisco's suggested (gold star) release. Check the release notes for the upgrade path and open security advisories.

  2. Get change approval and a maintenance window.

  3. Record the current state:

    • show version (release, and install mode should say INSTALL)

    • show switch (stack members, roles, all Ready)

    • show interfaces status, show cdp neighbors, show spanning-tree summary, show power inline

  4. Free up space: install remove inactive deletes old unused packages. Then dir flash: to check free space is larger than the image.

  5. Back up the config: copy running-config startup-config, then copy it to the backup server.

  6. If downloading from the internal repository, check the source interface and test reach to the cache first: ping <CACHE-SRV-IP> source <source-interface> (see the ISR SOP).

  7. Get the image's published MD5 hash.

Steps

  1. Download the image to the active switch:

    • copy http://repo.example.internal/firmware/cat9k_iosxe.<version>.SPA.bin flash:

  2. Verify the file: verify /md5 flash:cat9k_iosxe.<version>.SPA.bin. It must match the published hash.

  3. Install. Choose one:

    • One step: install add file flash:cat9k_iosxe.<version>.SPA.bin activate commit. Answer yes to the reload prompt. The install copies the image to every stack member.

    • Safer, with auto-rollback: install add file flash:cat9k_iosxe.<version>.SPA.bin activate, run the checks below, then install commit. If you don't commit before the auto-abort timer runs out, the switch rolls back to the old release on its own.

  4. Wait. The first boot can take longer if it also updates ROMMON or other low-level firmware. Do not power off the switch during this.

Check it worked

  • show version shows the new release on every member.

  • show switch shows all members Ready, same roles as before.

  • show install summary shows the new package as committed (after install commit if you used the safer option).

  • Interfaces, CDP neighbours, spanning tree and PoE match the pre-check records.

  • Users, phones and APs are back online.

Roll back

  • Not yet committed: install abort.

  • Already committed: show install rollback to list rollback points, then install rollback to id <id>.

Notes

  • Every member of a stack must run the same release. Turn on software auto-upgrade enable so a new or replacement member is upgraded to match when it joins.

  • Older Catalyst switches (e.g. 2960-X) run classic IOS, not IOS-XE, and have no install mode. On those: copy the .bin to flash:, verify the MD5, boot system flash:<image>.bin, write memory, reload.

  • Check the source interface before blaming a bad file or a dead cache, same as the ISR SOP.

Switch config backup and restore (any model, Cisco or Aruba)

PartDetail
PurposeSave any Cisco or Aruba switch's config off the box, and put it back when needed
When to useBackup: before any change or upgrade, and on a schedule. Restore: a bad change, a corrupted config, or replacement hardware
OutageBackup: none. Restore: possible, depending on the method

Process (same for every switch)

  1. Save the running config to startup.

  2. Snapshot on the device before a change.

  3. Copy off the box with SCP/SFTP where possible (TFTP is unencrypted). Name files <hostname>-<YYYYMMDD>.cfg.

  4. Check the file on the server is complete.

  5. Restore by replacing the config, never by merging over it.

  6. Check the restored config matches the backup, and you can still log in.

  • Interface names differ between models and vendors. A config from another model may need editing first.

OneNote section: Backups and restores  ·  Page: Cisco config backup and restore (IOS / IOS-XE)

Cisco config backup and restore (IOS / IOS-XE)

PartDetail
PurposeSave a device's config off the box, and put it back when needed
When to useBackup: before any change or upgrade, and on a schedule. Restore: a bad change, a corrupted config, or replacement hardware
OutageBackup: none. Restore: possible, depending on the method (see below)

Before you start

  1. Confirm you can reach the backup server from the device: ping <backup-server-ip> source <mgmt-interface>.

  2. Use SCP where possible. TFTP and FTP send the config, including password hashes and SNMP strings, unencrypted.

  3. Name files <hostname>-<YYYYMMDD>.cfg so they sort by device and date.

Backup steps

  1. Save the running config locally: copy running-config startup-config.

  2. Quick snapshot on the device before a change: copy running-config flash:<hostname>-<YYYYMMDD>.cfg.

  3. Copy off the box:

    • SCP: copy running-config scp://<user>@backup.example.internal/configs/<hostname>-<YYYYMMDD>.cfg

    • TFTP (if SCP isn't available): copy running-config tftp://<backup-server-ip>/<hostname>-<YYYYMMDD>.cfg

  4. Open the file on the server and check it's complete (ends with end).

Automatic backups (archive)

The archive feature saves a copy every time someone runs write memory, and on a timer:

archive
 path flash:archive/$h-
 maximum 10
 write-memory
 time-period 1440

$h = hostname. time-period is in minutes (1440 = daily). maximum only works for local flash paths. List saved copies with show archive. If the organisation uses a central backup tool, check the device is in it instead.

Restore steps

SituationMethodCommands
Undo a bad change on a live deviceReplace the running config with a saved fileconfigure replace flash:<file>.cfg list
Same, with a safety netReplace, auto-revert unless confirmedconfigure replace flash:<file>.cfg time 10, check, then configure confirm within 10 minutes (needs archive configured)
Replacement hardware or wiped deviceLoad the file as the startup config, then rebootcopy scp://<user>@backup.example.internal/configs/<file>.cfg startup-config, then reload

Do not use copy <file> running-config to restore. It merges the file into the current config instead of replacing it, so lines that should be gone stay in.

Check it worked

  • show archive config differences flash:<file>.cfg shows no unexpected differences from the backup.

  • Interfaces, VLANs, routing and neighbours match the pre-change records.

  • You can still log in over SSH.

Roll back

  • configure replace with time: don't confirm, and it reverts on its own.

  • Otherwise: configure replace back to the snapshot taken before the restore.

Notes

  • Replacement hardware: SSH keys are not stored in the config. Run crypto key generate rsa modulus 2048 after the restore, or SSH won't work.

  • Switches in VTP server or client mode keep VLANs in vlan.dat, not the config. Back up flash:vlan.dat too, or recreate the VLANs.

  • Interface names must match. A config from a different model may need editing first.

  • Licences are not in the config. Check show license summary on replacement hardware.

OneNote section: New device installs  ·  Page: New Cisco access switch install

New Cisco access switch install

PartDetail
PurposeInstall a new Catalyst access switch (or stack): pre-stage on the bench, then rack, connect and hand over
When to useNew site or comms room, extra ports, or replacing an old switch
OutageNew install: none. Replacement: yes, users on the old switch drop during the swap. Book a window

Before you start

  1. Get change approval.

  2. Get the allocations from IPAM or the network team: hostname (e.g. SW-ACCESS-01), management IP, gateway, VLANs.

  3. Check the site: rack space (RU), power circuits and UPS, PoE budget for phones and APs, uplink type (fibre SFP or copper) and patching plan.

  4. Record the serial number and check the licence.

  5. Replacement only: back up the old switch's config and record its port-to-VLAN map (show interfaces status, show cdp neighbors).

Stage on the bench

  1. Console in (9600 baud, 8N1). Answer no to the initial configuration dialog.

  2. Check the hardware: show version, show inventory.

  3. Upgrade to the latest supported release (see the Catalyst upgrade SOP).

  4. Stack only: connect stack cables and power, then set the intended active switch: switch 1 priority 15. Check with show switch.

  5. Apply the standard day-0 config: hostname, SSH only, AAA, NTP, logging, SNMPv3, management VLAN and IP, VLANs, access and trunk ports, spanning tree, unused ports shut. Template: Day-0 production config.

  6. Replacement only: match the old switch's port-to-VLAN map.

  7. Save and back up: copy running-config startup-config, then copy it to the backup server (see the backup SOP).

Install on site

  1. Rack and earth the switch. Connect each power supply to a different circuit if it has two.

  2. Connect the uplinks first. Check the trunk and management before patching any users.

  3. Test from the switch: ping <gateway-ip>, then SSH in from the management network.

  4. Patch access ports to the patching plan. Replacement: move cables one-for-one from the old switch.

  5. Label the switch and uplinks.

Check it worked

  • show interfaces trunk: uplinks trunking with the right allowed VLANs and native VLAN.

  • show cdp neighbors: the upstream switch seen on the expected ports.

  • show spanning-tree summary: no unexpected blocked ports. This switch is not root.

  • show interfaces status: user ports up in the right VLANs.

  • show power inline: phones and APs powered, budget not exceeded.

  • show ntp associations: time synced.

  • Monitoring (SNMP), syslog and the backup system can see the switch.

  • Users, phones and APs work.

Roll back

  • New install: shut the uplink port on the upstream switch, fix the config over console, try again.

  • Replacement: move the cables back to the old switch (keep it racked until the new one is proven).

Notes

  • Uplinks before users: patching users onto a switch with a wrong trunk or STP setup can cause a loop or outage.

  • BPDU Guard and PortFast on access ports only, never on uplinks.

  • Update the records after: IPAM, network diagram, asset register, monitoring.

Baseline settings

  • CIMC on the management VLAN, not a user VLAN.

  • Default admin password changed.

  • NTP and syslog set, so logs have correct times and are kept off the box.

  • SNMP or email alerts on for hardware faults.
